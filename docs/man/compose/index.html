$ dok compose

Compose projects as declared against as running: missing services, orphans, replicas short of the count

Synopsis

dok compose [OPTIONS] [PROJECT]

Description

A compose project checked against its own compose files. With no argument, one line per project: services up of those declared, containers running, and what is wrong. With a project name, one row per service: replicas running of those declared, image, status and ports, and a line per replica when there are several, so the one that died shows.

Services the files declare that never started are missing. Containers whose service is no longer in the files are orphans, which docker compose up --remove-orphans would remove. Services behind a profile that is not active are shown dimmed rather than reported, and docker compose run containers are listed apart instead of being counted as replicas. Replica counts come from deploy.replicas or scale; files are merged in the order compose was given them, and top-level include is followed.

Everything else comes from the labels compose writes on each container. The files are only read when the daemon is on this machine: through a remote context their paths are the remote host's, so dok says the check was skipped instead of guessing.

Arguments

[PROJECT]
Project to show in detail; omit for every project

Options

-c, --context <NAME>
Docker context to use (see docker context ls); overrides DOCKER_HOST, DOCKER_CONTEXT and the current context

Every command also takes the global options: --json, --color, --icons and --theme.

Examples

$ dok compose  # every project, and which ones are not as declared
$ dok compose shop  # one project, service by service; a prefix is enough
$ dok compose shop --json  # the same, for a script
